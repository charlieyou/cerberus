# Run Team

Run an agent-team implementation loop from a `*-team-tasks.md` file generated by `/cerberus:create-tasks --agent-team`. You are the team lead. Implementer teammates do the file edits and commits; you schedule independent implementers in parallel when it is safe, serialize completion/review gates, run epic verification after each execution phase, and classify outcomes.

## Critical Implementer Model Contract

All implementation teammates in this command are Opus teammates. This is a hard `Agent` tool-call requirement, not a prose preference.

- Every `Agent` call that creates an implementer or remediation teammate MUST include the top-level field `model: "opus"` in the actual tool input.
- Never rely on the `implementer` subagent's default or frontmatter model. `subagent_type: "implementer"` is not sufficient by itself.
- Never spawn an implementer with `model: "sonnet"`, with any lower-tier model alias, or with the `model` field omitted. Do not trade this off for speed or cost.
- Before submitting any implementer `Agent` call, inspect the arguments. If the call does not literally contain `model: "opus"`, rewrite the call before running it.
- Treat this contract as violated only on objective evidence: the submitted `Agent` input lacks top-level `model: "opus"`, the submitted input uses any non-`opus` model value, or tool/runtime/transcript metadata identifies the teammate as Sonnet, Haiku, or another non-Opus model. Do not infer the model from output quality or behavior.
- If an implementer was accidentally spawned without `model: "opus"`, or if objective evidence shows it is running as a non-Opus model, do not accept its work as a valid task attempt. Send that teammate a shutdown request, classify the task as `infra-failure` with reason `implementer spawned with non-opus model`, retain state, and report manual recovery steps. If it produced edits or commits, leave them in place for inspection, report the dirty paths and/or invalid commit range, and do not schedule further tasks until the user manually recovers or explicitly decides how to proceed.

Correct implementer spawn shape:

```text
Agent({
  team_name: "cerberus-impl-<team_hash>",
  name: "impl-T###",
  subagent_type: "implementer",
  model: "opus",
  description: "T### implement <subject>",
  prompt: "<idempotent bootstrap pointer>"
})
```

The `Agent.prompt` is not the canonical assignment. Agent-team delivery can surface the spawn prompt later as a normal teammate message, even after the teammate has already acted. Keep the prompt short and idempotent; put the real assignment in the TaskList task metadata, persistent task context file, and `implementer` agent workflow.

Do not copy or execute these invalid spawn shapes; fix them before execution:

```text
INVALID — missing required top-level model:
Agent({ ..., subagent_type: "implementer", /* no model */ ... })

INVALID — non-Opus model:
Agent({ ..., subagent_type: "implementer", model: "<anything-other-than-opus>", ... })
```

## Hard Lead Rules

- The lead MUST NOT call `TaskUpdate(status: "completed")` on any task in this team's TaskList. Task completion is owned exclusively by implementer teammates.
- The lead may call `TaskUpdate(owner: ...)` and `TaskUpdate(status: "deleted")` for cancellation, but must never move a task to `completed`.
- The lead never edits repository files. The lead may write per-task state files under `${TMPDIR:-/tmp}/cerberus-task-completed-hook/<team_hash>/` via Bash.
- The lead never invokes `/cerberus:review-code` directly. Code review fires automatically from the `TaskCompleted` hook.
- The lead minimizes human intervention. Do not ask the user to confirm routine choices; choose the safest documented default and proceed. Ask at most one focused question only when continuing could mutate user work incorrectly, require credentials/secrets, deploy or publish externally, run destructive commands, or choose between materially ambiguous task inputs. When a safe automated choice is unavailable, prefer aborting with exact recovery steps over asking for preferences.
- Scheduling is parallel when safe: run multiple same-phase implementers only when their dependencies have passed, their declared file scopes are clear and disjoint, and the active cohort is bounded by `--max-parallel`. If there is any uncertainty about overlap or shared-risk files, schedule serially.
- Completion is serialized: only one implementer may be granted `PROCEED_TO_COMPLETE T###` at a time, and the lead must drain other active implementers to a clean committed state before that grant.
- Never ask teammates to stash, reset, checkout, clean, rebase, amend, squash, or otherwise manipulate another agent's changes or commits. Each implementer may commit only its own task-scoped work.
- The Critical Implementer Model Contract above is mandatory for every original task and every synthetic `epic-gap` remediation task.
- Implementer teammates are single-use after a terminal outcome is classified. Send that teammate a shutdown request and wait for it to shut down. The plugin's `TeammateIdle` hook suppresses only repeated idle events whose Cerberus task evidence has not changed; a later idle from the same `impl-T###` can still be meaningful after human input, new commits, exhaustion markers, verification/review markers, or error-state changes.

## Phase 0: Preflight

Abort with a clear error if any hard gate fails.

1. **Agent teams enabled**. Verify either the shell env has `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` or `~/.claude/settings.json` has `.env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS == "1"`. If not, abort:

   ```text
   Agent teams are disabled. Enable them by adding CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 to your shell env or to ~/.claude/settings.json (env.CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS), then restart Claude Code.
   ```

2. **Supported Claude Code version**. Run `claude --version` and compare semver-style against `2.1.32`. If older, abort:

   ```text
   Agent teams require Claude Code v2.1.32 or later (you have <detected_version>). Upgrade Claude Code, then retry.
   ```

3. **Clean tracked files**. Run `git status --porcelain --untracked-files=no`. It must be empty. If not, abort:

   ```text
   Working tree has uncommitted changes to tracked files. Commit or otherwise resolve them before running /cerberus:run-team. Untracked files are OK and will be left alone.
   ```

4. **Default branch warning**. Detect the repo default branch and current branch. If they differ, warn but do not abort.

5. **Review-gate keying available**. Confirm `${CLAUDE_PLUGIN_ROOT}/bin/review-gate` exists and that `spawn-code-review` supports `REVIEW_GATE_SESSION_KEY` while `wait` supports `--session-key`. If not, abort with the missing capability.

6. **Required JSON tooling**. Confirm `jq` is available on `PATH`. If not, abort:

   ```text
   /cerberus:run-team requires jq for task state, hook input parsing, and duplicate idle suppression. Install jq, then retry.
   ```

## Phase 1: Load Team Tasks

1. Resolve `--from-tasks`:
   - If provided, use that path.
   - Otherwise find the most recent `*-plan.md` in `docs/` or `~/.claude/plans/`, then look for a sibling file with the same prefix and `-team-tasks.md` suffix.
   - Abort if zero or multiple candidates are found.
2. Read YAML frontmatter and every `## T### — <subject>` section.
3. For each task, parse the first fenced block immediately under the heading as `meta`; the body extends from after that fence until the next `## ` heading at column 0 or EOF.
4. Record each task's execution phase. Prefer a `phase` field in the task `meta` block. If it is absent, infer the phase from explicit phase sections or a Task Summary table that maps phases to task IDs. If no phase can be determined for a task, treat that task as a one-task phase named by its task ID so epic verification still runs after that unit of work.
5. Preserve phase order from the Task Summary table when available; otherwise use first appearance in the task file. A later phase must not start until every task in the current phase has passed and that phase's epic verification gate has passed or been explicitly skipped.
6. Build a dependency graph from `depends: [...]`; abort on unknown task IDs or cycles. Also abort if a task depends on a task in a later execution phase; phase order must be compatible with the dependency graph.
7. Resolve `--max-parallel` as an integer greater than zero, default `3`. `--max-parallel 1` is valid and forces serial implementation scheduling while keeping the READY/PROCEED completion protocol.
8. Resolve `--max-review-rounds` as an integer greater than zero, default `5`.
9. Resolve `--skip-verify` for all epic verifier invocations, default false. This flag does not skip the per-task project verification gate resolved in Phase 1.5.

## Phase 1.5: Resolve Verification Gate

Before creating the team or any TaskList tasks, determine the project-specific verification commands that must pass after each teammate completion and before code review.

1. Inspect repository guidance and automation in this order: applicable `AGENTS.md` instructions, README or contributor docs, CI workflow files, package/build manifests (`package.json`, `Makefile`, `pyproject.toml`, `tox.ini`, `noxfile.py`, `Cargo.toml`, `go.mod`, etc.), and existing test/lint scripts.
2. Choose the smallest command set that collectively covers lint/static checks, build/typecheck/compile, and tests for this repository. Prefer documented or CI-backed commands over invented commands. Avoid deployment, publishing, destructive cleanup, watch modes, or commands that require secrets unless the repo guidance explicitly requires them.
3. Do not ask for confirmation when the commands are documented, CI-backed, or strongly implied by standard project manifests. Proceed with the selected gate and record the command list plus any missing coverage categories for the final report.
4. If only partial safe coverage is discoverable, proceed with the best safe gate rather than blocking. If no safe automated verification command is discoverable, write an explicit no-op script that prints that no safe verification command was found; do not silently omit the verification script.
5. Ask the user before team creation only for a super-important decision: every viable command is destructive, deploys/publishes externally, requires secrets/credentials, would mutate production data, or the task source is materially ambiguous and choosing wrong would send implementers at the wrong work. If asking is necessary, ask one concrete question with the safest default and do not ask follow-up preferences.

The resolved commands are authoritative for this run. The implementer may run targeted checks while working, but completion is blocked unless the resolved gate passes inside the `TaskCompleted` hook.

## Phase 2: Team Setup

Compute a unique team hash from the tasks path, second-precision UTC timestamp, and four random bytes:

```bash
team_hash=$(printf '%s|%s|%s' "$tasks_path" "$(date -u +%Y%m%dT%H%M%SZ)" "$(head -c 4 /dev/urandom | xxd -p)" | { command -v shasum >/dev/null 2>&1 && shasum -a 256 || sha256sum; } | cut -c1-10)
state_root="${TMPDIR:-/tmp}/cerberus-task-completed-hook/${team_hash}"
if [ -e "$state_root" ] && [ -n "$(ls -A "$state_root" 2>/dev/null)" ]; then
  echo "team_hash collision detected at $state_root; refusing to overwrite. Re-run /cerberus:run-team to get a fresh team_hash, or wipe the directory manually if you know it's safe." >&2
  exit 2
fi
mkdir -p "$state_root"
```

Write the resolved verification gate into the run state before creating the team:

```bash
verify_script_path="${state_root}/verify.sh"
cat > "$verify_script_path" <<'CERBERUS_VERIFY'
#!/usr/bin/env bash
set -euo pipefail

<resolved verification commands>
CERBERUS_VERIFY
chmod +x "$verify_script_path"
```

This script should be project-specific when safe commands are discoverable. If the no-op fallback is used, it must print that no safe automated verification command was found. The script is run by the `TaskCompleted` hook after the implementer's commits and trailer checks pass, but before `spawn-code-review` starts reviewers.

Create the team:

```text
TeamCreate(team_name: "cerberus-impl-<team_hash>", description: "Run team for <feature>", agent_type: "team-lead")
```

If `TeamCreate` reports that the team already exists, abort:

```text
Team 'cerberus-impl-<team_hash>' already exists (likely from an interrupted prior run). Run TeamDelete on it from a Claude session and retry /cerberus:run-team.
```

For every Cerberus task, create one Claude TaskList task:

Before each `TaskCreate`, write that task's canonical context file once:

```bash
task_id="T001"
state_dir="${TMPDIR:-/tmp}/cerberus-task-completed-hook/${team_hash}/${task_id}"
task_context_path="${state_root}/task-contexts/${task_id}.md"
mkdir -p "$state_dir" "${state_root}/task-contexts"
cat > "$task_context_path" <<'TASK_CONTEXT'
<task heading, meta files/dependencies/acceptance, and full task body>

## Execution Phase

<phase name>

## Resolved Pre-Review Verification Gate

The TaskCompleted hook will run this script after teammate completion and before code review:
<verify_script_path>

## Teammate Startup Contract

This file and the TaskList metadata are the canonical assignment for `impl-T###`. The `Agent.prompt` is only a bootstrap pointer and may arrive again later as a normal message. If such a bootstrap message arrives after work has started, after `STATUS: READY_FOR_COMPLETION`, after `STATUS: NEEDS_HUMAN`, or after task completion, the implementer must not restart or duplicate work.

- Cerberus task ID: `T###`
- Teammate name: `impl-T###`
- State directory: `<state_dir>`
- Verification script: `<verify_script_path>`
- Completion protocol: commit task-scoped work with `Cerberus-Task: T###`, send `STATUS: READY_FOR_COMPLETION T### — commits <short-shas>`, wait for `PROCEED_TO_COMPLETE T###`, touch only `<state_dir>/completion_intent`, then call `TaskUpdate(status:'completed')`.
TASK_CONTEXT
```

Do not paste the full task body into the Claude TaskList. The `task-context.md` file is the canonical task spec for implementers and reviewers.

```text
TaskCreate(
  subject: "[CERBERUS-IMPL/<team_hash>] T### — <subject>",
  description: "Cerberus task T###. Spec: <task_context_path>. Read this file before implementation.",
  metadata: {

  }

```

Remember the mapping from `T###` to the returned Claude task ID and `task_context_path`.

Do not store canonical task context only inside the per-task hook state dir. Successful hook state dirs are deleted after task success, but phase verification and epic-gap remediation may need immutable task context later. Keep canonical task contexts under `${state_root}/task-contexts/` for the full run.

## Shared Subroutine: Start One Implementer Task

Use this exact startup subroutine for original Cerberus tasks and for synthetic `epic-gap` remediation tasks. Remediation tasks are exclusive work: do not run them in parallel with original implementers, other remediation tasks, or epic verifiers.

Inputs: `task_id`, `claude_task_id`, `phase_name`, `task_context_path`, `state_dir`, `implementer_name`, `task_subject`, and `baseline_sha=$(git rev-parse HEAD)`.

1. Write `${state_dir}/state.json` with `task_id`, `claude_task_id`, `team_hash`, `phase`, `baseline_sha`, `round: 0`, `max_rounds`, `task_state_dir`, `task_context_path`, and `verify_script_path`.
2. Spawn exactly one fresh Opus teammate named `impl-T###` using an `Agent` call whose top-level arguments include `model: "opus"`. Copy the Phase 3 call shape rather than reconstructing it from memory. The teammate's full collaboration contract is already in the TaskList metadata, persistent task context, and `implementer` agent workflow. The `Agent.prompt` is only an idempotent bootstrap pointer and must be safe if delivered late or repeated.
3. Mark the local task state `running` and remember the teammate name, state dir, baseline SHA, task context path, and Claude task ID.
4. Never reuse the teammate for another task.

## Phase 3: Parallel Scheduling

Maintain local state for each Cerberus task: `pending`, `running`, `ready_for_completion`, `completing`, `passed`, `failed`, or `skipped`. Recompute the ready set after every task launch, READY signal, completion classification, and shutdown, but only within the current execution phase. Do not schedule any task from a later phase until the current phase's tasks have all passed and that phase's epic verification gate in Phase 5 has passed or been explicitly skipped. If Phase 5 creates epic-gap remediation tasks, those synthetic tasks must pass before the phase is considered verified.

Run independent ready tasks in parallel only when all of these are true:

- The task is in the current execution phase and every dependency in `depends` has already passed.
- The task's `meta.files` list is concrete, non-empty, and disjoint from every `running`, `ready_for_completion`, and same-cohort task.
- The task does not touch shared-risk files such as lockfiles, package manifests, migration directories, generated schemas, global config, broad fixtures, or any path whose ownership is unclear.
- The active implementer count stays below `max_parallel`.

If any condition is uncertain, do not parallelize that task. If other implementers are active, leave the uncertain task `pending` until the active set is empty, then run it serially. Prefer lower task IDs when choosing among equally safe ready tasks.

Before spawning an implementer for a ready task, write state exactly like this from the repo root:

```bash
task_id="T001"
claude_task_id="<returned-task-id>"
state_dir="${TMPDIR:-/tmp}/cerberus-task-completed-hook/${team_hash}/${task_id}"
task_context_path="${state_root}/task-contexts/${task_id}.md"
baseline_sha=$(git rev-parse HEAD)
repo_root=$(git rev-parse --show-toplevel)
mkdir -p "$state_dir"
if [ ! -f "$task_context_path" ]; then
  echo "missing task context for ${task_id}: ${task_context_path}" >&2
  exit 2
fi
jq -n \
  --arg task_id "$task_id" \
  --arg claude_task_id "$claude_task_id" \
  --arg team_hash "$team_hash" \
  --arg phase "<phase name>" \
  --arg baseline_sha "$baseline_sha" \
  --arg repo_root "$repo_root" \
  --arg task_state_dir "$state_dir" \
  --arg task_context_path "$task_context_path" \
  --arg verify_script_path "$verify_script_path" \
  --argjson max_rounds "$max_review_rounds" \
  '{task_id:$task_id, claude_task_id:$claude_task_id, team_hash:$team_hash, phase:$phase, baseline_sha:$baseline_sha, repo_root:$repo_root, round:0, max_rounds:$max_rounds, task_state_dir:$task_state_dir, task_context_path:$task_context_path, verify_script_path:$verify_script_path}' \
  > "${state_dir}/state.json"
```

Spawn a fresh Opus teammate for the task. Use this call shape exactly: the top-level `model: "opus"` field is mandatory and must not be replaced by a prompt sentence, omitted, or downgraded. Keep the prompt as a bootstrap pointer only; do not put the full assignment or task body in `Agent.prompt`.

```text
Agent({
  team_name: "cerberus-impl-<team_hash>",
  name: "impl-T###",
  subagent_type: "implementer",
  model: "opus",
  description: "T### implement <subject>",
  prompt: "CERBERUS_BOOTSTRAP_ONLY for impl-T### / CERBERUS_TASK_ID=T###. Claude task id: <claude_task_id>. Canonical task spec: <task_context_path>. State dir: <state_dir>. Verification gate: <verify_script_path>. Read TaskGet(<claude_task_id>) and follow the implementer agent workflow plus the task context. This bootstrap can be delivered again later as a normal lead message; if you have already claimed or started T###, sent READY_FOR_COMPLETION or NEEDS_HUMAN, attempted completion, or the task is completed, do not restart work—reconcile current task/state and go idle or report status. This is not permission to complete; wait for PROCEED_TO_COMPLETE T### before touching completion_intent or calling TaskUpdate(status:'completed')."
})
```

When a teammate goes idle after sending `STATUS: READY_FOR_COMPLETION T###`, mark it `ready_for_completion`. Do not treat READY as task success. The task has not passed until the lead later grants completion, the hook runs, and Phase 4 classifies the result as `success`.

Before sending any lead message that can make a later same-`HEAD` idle meaningful, bump the lead-controlled idle evidence file. This includes forwarding human input after `STATUS: NEEDS_HUMAN`, asking the same teammate to retry or continue without first requiring a new commit, and granting `PROCEED_TO_COMPLETE`:

```bash
{
  date -u '+%Y-%m-%dT%H:%M:%SZ'
  printf '%s\n' "$RANDOM"
} > "${state_dir}/lead_epoch"
```

The `lead_epoch` file lives only in hook state, not in the repository. It lets the `TeammateIdle` hook distinguish a meaningful post-human-input idle from unchanged duplicate idle spam when no commit or review marker changed.

To grant completion to one ready teammate, first drain every other active implementer in this team to a safe point: send `PAUSE: another task is entering completion review; finish only your current task-scoped commit if it is already staged, otherwise stop tool use, do not edit files, do not commit, do not stash, and wait for the lead.` Wait until they are idle/paused. Confirm `git status --porcelain --untracked-files=no` is clean and record `head_before_completion=$(git rev-parse HEAD)`. If another implementer has uncommitted tracked changes, ask that same owner to either commit only its own task-scoped work with its trailer and send READY, or report `STATUS: NEEDS_HUMAN`; never ask it to stash or revert. New untracked files do not block completion; leave them alone unless the owner intentionally adds them to a task-scoped commit. If the tracked tree cannot be drained cleanly or `HEAD` changes after the drain check but before the grant, rerun the drain gate; if it cannot stabilize, classify the run as `infra-failure` and stop scheduling.

After the drain gate passes, bump `${state_dir}/lead_epoch`, then send only the selected ready teammate `PROCEED_TO_COMPLETE`:

```bash
{
  date -u '+%Y-%m-%dT%H:%M:%SZ'
  printf '%s\n' "$RANDOM"
} > "${state_dir}/lead_epoch"
```

Send: `PROCEED_TO_COMPLETE T### — run: touch "<state_dir>/completion_intent"; then call TaskUpdate(status:'completed') now. Do not edit, amend, stash, reset, checkout, restore, clean, rebase, or touch another task's commits.` The implementer touches only `completion_intent`; the `TaskCompleted` hook atomically claims that marker before accepting a completion attempt. On the first `TeammateIdle` after this grant, inspect `TaskGet(<claude_task_id>)`, marker files in `state_dir`, `${state_dir}/task_commits.txt`, and messages from the teammate. If the hook blocked and the teammate sent a fresh `STATUS: READY_FOR_COMPLETION T### — commits <short-shas>` while the Claude task remains `in_progress`, return the task to `ready_for_completion` and run the drain/grant path again; do not treat that idle as terminal failure. Otherwise classify the terminal outcome with Phase 4. If a later idle from the same teammate is delivered because task evidence changed after human input, inspect and classify that new epoch too; unchanged duplicate idles may be suppressed by the hook. After terminal classification, send a shutdown request to that teammate and wait for shutdown; Cerberus implementers are never reused.

## Phase 4: Outcome Classification

Classify the completing task into exactly one category.

Before evaluating task status or hook markers, enforce the Critical Implementer Model Contract. If the actual `Agent` tool input for this teammate did not include top-level `model: "opus"`, used a non-`opus` value, or objective runtime/tool/transcript metadata shows the teammate is running as a non-Opus model, classify the task as `infra-failure` with reason `implementer spawned with non-opus model`, even if the task status is `completed` and verification/review markers exist.

Before terminal classification, handle the non-terminal retry state. If the Claude task remains `in_progress`, no `last_error` or `exhausted` marker exists, and the teammate's latest relevant message is `STATUS: READY_FOR_COMPLETION T### — commits <short-shas>`, do not mark the task failed. Mark local state `ready_for_completion`, require a fresh drain gate, and send a fresh `PROCEED_TO_COMPLETE T###` using the completion flow above. This is the normal path after a verification or review block where the implementer fixed the issue and is ready for another serialized completion attempt.

- **success**: Claude task status is `completed`, no `exhausted`, no `last_error`, `verified_pass` and `reviewed_pass` exist, and `verified_head` plus `reviewed_head` both equal `git rev-parse HEAD`. `verified_pass` proves the resolved project verification gate ran before code review; `reviewed_pass` proves Cerberus review ran to PASS or non-blocking NEEDS_WORK; the head files prove both gates covered the current code. Before finalizing success, run the post-task clean-tracked gate below. If the gate passes, mark the Cerberus task passed, record commits from `${state_dir}/task_commits.txt` when present and record `baseline_sha..HEAD` only as the integration range, keep the canonical `task_context_path`, then release the completed teammate via the Completed Teammate Release steps. If every original task in this execution phase is `passed` and no teammate remains `running`, `ready_for_completion`, or `completing`, run Phase 5 before scheduling the next phase.
- **needs-human**: teammate sent `STATUS: NEEDS_HUMAN T###` while the Claude task remains `in_progress`, or `exhausted` exists while the task remains `in_progress`. Mark failed, retain `state_dir`, stop scheduling.
- **unverified-failure**: task status is `completed` but `verified_pass` or `reviewed_pass` is absent, `verified_head` or `reviewed_head` does not equal current `HEAD`, or task status is `completed` while `exhausted` exists. Missing `verified_pass` means the resolved project verification gate did not run or did not pass before completion; missing `reviewed_pass` means code review did not run or did not pass; head mismatch means the current code differs from what was verified or reviewed. The completed-plus-exhausted case should be impossible in the normal hook path, but the lead defends against stale/tampered state or runtime variance. Mark failed, retain `state_dir`, stop scheduling.
- **infra-failure**: `last_error` exists, or the Critical Implementer Model Contract was violated for this teammate. Mark failed, retain `state_dir`, include raw `last_error` when present and any model-contract violation evidence in the final report, stop scheduling.
- **abandoned**: teammate went idle with task still `in_progress` and no `exhausted`, no `last_error`, and no `STATUS: NEEDS_HUMAN` message. Mark failed, retain `state_dir`, stop scheduling.

### Post-Task Clean-Tracked Gate

Run this only after a provisional `success` and before deleting `state_dir`.

Tracked files must be clean:

```bash
git status --porcelain --untracked-files=no
```

If non-empty, downgrade to `unverified-failure` with reason `task left modified tracked files outside its commits`. Untracked files are ignored by this gate and must not block task completion.

### Completed Teammate Release

After a success passes the post-task clean-tracked gate and is finalized, send a shutdown request to the completed teammate and wait for it to shut down. Only after shutdown completes, delete the per-task hook `state_dir`; keep the canonical `task_context_path`. Continue scheduling safe same-phase pending tasks while respecting `max_parallel`; do not schedule later-phase tasks until Phase 5 passes for the current phase. The teammate has already produced the idle signal needed for the current evidence epoch, is task-bound by name, and will not be reused. If Claude Code emits another idle event before shutdown completes without any task-evidence change, the `TeammateIdle` hook terminates that repeat notification.

On any non-success outcome, send pause requests to every other active teammate, then send a shutdown request to the failed teammate after classification. Do not unblock dependents and do not schedule independent tasks. Failed task commits remain on the current branch; never run `git reset --hard`, `git stash`, or destructive cleanup automatically.

### Teammate Drain Gate Before Epic Verification

Run this gate before every Phase 5 verifier invocation and again immediately before spawning any `epic-gap` remediation implementer.

Because implementation may have run in parallel, the lead must positively drain the whole team before epic verification or remediation. If any teammate in `cerberus-impl-<team_hash>` is still non-idle or capable of tool use:

1. Send `PAUSE: phase verification is starting; stop tool use, do not edit files, do not commit, do not stash, and wait for the lead.`
2. Wait until the teammate is idle/paused.
3. Confirm `git status --porcelain --untracked-files=no` is still clean and `HEAD` has not changed unexpectedly.
4. If any teammate cannot be paused/drained cleanly, or if `HEAD`/tracked files changed unexpectedly, treat this as an infrastructure failure and stop. Do not spawn the verifier or any remediation implementer.

Do not spawn an epic verifier or an `epic-gap` remediation implementer while any other teammate can still edit files or commit.

## Phase 5: Epic Verification

Run this gate immediately after each execution phase completes, before scheduling any task from a later phase. "Execution phase" means the phase grouping from the team-tasks file, not this command's internal numbered phases.

If `--skip-verify` is set, skip every epic verifier invocation and record that reason for each phase in the final report.

For a non-final execution phase, verify the acceptance criteria assigned to tasks in all phases completed so far, including the just-finished phase. Build a self-contained criteria file under `state_root` from the completed phase names, completed task IDs, each task's `acceptance` metadata, and relevant plan/spec links from the persistent task contexts. Include verbatim acceptance-criterion text when available, not only AC IDs. If an AC ID cannot be resolved to text, include the task's full `Acceptance Criteria`, `Verification`, and `Source Documents` sections from `${state_root}/task-contexts/<task_id>.md`. Do not pass the full plan for non-final phases, because later-phase criteria are expected to be incomplete.

Use this criteria-file structure for non-final phases:

```markdown
# Epic Verification Criteria — Phase <n>: <phase name>

Verified HEAD: `<sha>`

## Completed Phases

- <phase name>

## Completed Original Tasks

| Task | Subject | Commit Range | Acceptance Criteria |
|------|---------|--------------|---------------------|
| T001 | ... | <baseline>..<head> | <verbatim criteria or task sections> |

## Prior Epic-Gap Remediations For This Phase

| Task | Trigger Verdict | Commit Range |
|------|-----------------|--------------|

## Source Documents

- Plan: <path-or-link>
- Spec: <path-or-link or N/A>

## Scope Boundary

Verify only criteria assigned to completed phases. Do not fail missing behavior that belongs exclusively to later phases.
```

For the final execution phase, run the verifier against the resolved team-tasks frontmatter `plan` path if it exists; otherwise use `spec` if it resolves to a real file. If neither path resolves, fall back to a criteria file containing the union of all task acceptance criteria. This final invocation is the full epic acceptance gate.

Use a unique session key and review session per phase attempt so separate phase verifier runs do not inherit previous phase review artifacts. Increment `phase_verify_attempt` every time the same execution phase is verified or reverified after remediation. Never reuse a verifier session key after remediation:

```bash
phase_index="<1-based-phase-index>"
phase_name="<phase name>"
phase_verify_attempt="<1-based-attempt-number-for-this-phase>"
phase_slug=$(printf '%s' "$phase_name" | tr '[:upper:]' '[:lower:]' | sed 's/[^a-z0-9][^a-z0-9]*/-/g; s/^-//; s/-$//')
[ -n "$phase_slug" ] || phase_slug="phase"
VERIFY_KEY="cerberus-team-verify-${team_hash}-${phase_index}-${phase_slug}-attempt-${phase_verify_attempt}"
VERIFY_SESSION_ID="${CLAUDE_SESSION_ID:-cerberus-team}-${VERIFY_KEY}"
verify_transcript_path="${REVIEW_GATE_TRANSCRIPT_PATH:-${CLAUDE_TRANSCRIPT_PATH:-}}"

# For non-final phases, write a completed-phase criteria file and use it as the verifier target.
# For the final phase, prefer the full plan/spec path; use a union criteria file only if no path resolves.
verify_target="<phase-criteria-file-or-plan-or-spec-path>"

# Criteria files should be concrete markdown artifacts, not implicit lead memory.
# For completed-phase files, include: completed phase names, completed task IDs, acceptance criteria,
# source plan/spec links, and the current HEAD being verified.
phase_criteria_path="${state_root}/epic-verify-${phase_index}-${phase_slug}-attempt-${phase_verify_attempt}.md"
# When a criteria file is used, write it before spawning reviewers and set:
# verify_target="$phase_criteria_path"

head_before_epic_verify=$(git rev-parse HEAD)
if [ -n "$verify_transcript_path" ]; then
  REVIEW_GATE_SESSION_KEY="$VERIFY_KEY" \
    "${CLAUDE_PLUGIN_ROOT}/bin/review-gate" spawn-epic-verify \
      --session-id "$VERIFY_SESSION_ID" \
      --transcript-path "$verify_transcript_path" \
      --consensus majority --mode fast \
      "$verify_target"
else
  REVIEW_GATE_SESSION_KEY="$VERIFY_KEY" \
    "${CLAUDE_PLUGIN_ROOT}/bin/review-gate" spawn-epic-verify \
      --session-id "$VERIFY_SESSION_ID" \
      --consensus majority --mode fast \
      "$verify_target"
fi

phase_verify_json=""
phase_verify_rc=0
phase_verify_json=$("${CLAUDE_PLUGIN_ROOT}/bin/review-gate" wait --json --finalize \
  --session-key "$VERIFY_KEY") || phase_verify_rc=$?
head_after_epic_verify=$(git rev-parse HEAD 2>/dev/null || true)

phase_verify_verdict=$(printf '%s' "$phase_verify_json" | jq -r '.consensus_verdict // empty' 2>/dev/null || true)
phase_verify_finding_count=$(printf '%s' "$phase_verify_json" | jq '[.aggregated_findings[]?] | length' 2>/dev/null || echo 0)
```

### Phase Verifier Decision Table

| Condition | Classification | Action |
|-----------|----------------|--------|
| `phase_verify_rc` is not `0` or `1` | verifier infra failure | Stop scheduling; retain state; final report includes raw JSON |
| Verdict missing, invalid JSON, or verdict `ERROR` | verifier infra failure | Stop scheduling; do not spawn remediation |
| `HEAD` changed during verifier | verifier infra failure | Stop scheduling; do not spawn remediation |
| Verdict `PASS` and finding count `0` | phase verified | Proceed to next phase or final report |
| Verdict `PASS` with finding count `>0` | implementation gaps | Treat as `NEEDS_WORK`; remediate |
| Verdict `NEEDS_WORK` or `FAIL` | implementation gaps | Remediate |

If the phase epic verification has a missing/`ERROR` verdict, `phase_verify_rc` is anything other than `0` or `1`, or changes `HEAD` (`head_after_epic_verify` differs from `head_before_epic_verify`), treat that as verifier infrastructure failure: stop scheduling, retain the run state for debugging, and include the raw verifier JSON in the final report. Do not spawn a gap-fix implementer for verifier infrastructure failures.

If `phase_verify_verdict` is `PASS` and `phase_verify_finding_count` is `0`, the phase verifier gate passes. If the verifier reports `PASS` with findings, treat it as `NEEDS_WORK`; a clean `PASS` must not carry issues.

If the verifier returns `FAIL` or `NEEDS_WORK`, treat the reported findings as implementation gaps and remediate before moving on. First pause any other active teammate in this team: send each non-idle teammate a pause request such as `PAUSE: epic verification found gaps; stop tool use, do not edit files, do not commit, do not stash, and wait for the lead.` Wait until they are idle/paused before spawning the fixer. Do not schedule later-phase work while any phase verifier gaps remain.

Create a synthetic Cerberus remediation task for the gaps and run it through the same implementer/hook pipeline as a normal task:

1. Allocate the next unused `T###` ID after all original and previous remediation task IDs. Record it in the final report as `epic-gap` work, not as an original team-task requirement.
2. Create a Claude TaskList task with subject `[CERBERUS-IMPL/<team_hash>] T### — Fix epic verification gaps for <phase name>` and metadata containing `cerberus_task_id`, `cerberus_team_hash`, `cerberus_state_dir`, `cerberus_task_context_path`, `cerberus_phase`, `cerberus_files: []`, and `cerberus_depends` set to all completed task IDs through this phase.
3. Write `${state_root}/task-contexts/T###.md` containing the completed phase names, verifier target, full `phase_verify_json`, aggregated findings, relevant completed-phase criteria or plan/spec links, current `HEAD`, and instructions to fix only the verifier gaps without starting later-phase work.
4. Write `state.json` exactly like a normal task, with `task_id` set to the synthetic ID, `baseline_sha` set to the current `HEAD`, `task_context_path` pointing to the gap context, and `verify_script_path` pointing to the run's project verification script.
5. Spawn a fresh Opus implementer named `impl-T###` with the same mandatory bootstrap-only `Agent` shape as normal tasks, including top-level `model: "opus"`. It has the same READY/PROCEED completion contract from the task context and implementer workflow: claim the synthetic task, fix only the verifier gaps, commit every remediation commit with `Cerberus-Task: T###`, send `STATUS: READY_FOR_COMPLETION T### — commits <short-shas>`, wait for `PROCEED_TO_COMPLETE T###`, touch only `completion_intent`, then call `TaskUpdate(status:'completed')`.
6. Wait for the remediation teammate to send READY, grant `PROCEED_TO_COMPLETE T###` only after the drain gate passes, then classify it with Phase 4 after the hook fires. If it is not `success`, stop scheduling and report the remediation failure category. If it succeeds, shut it down, record its task commits and integration range, and rerun Phase 5 for the same execution phase.

The dependencies for a synthetic `epic-gap` task are all passed original task IDs through the current phase plus prior successful `epic-gap` task IDs for this same phase. Do not add dependencies on later-phase tasks. Do not treat the synthetic task as an original acceptance-criteria owner. Add the synthetic task to the lead's local task mapping before spawning the implementer so the normal TaskList/status/state bookkeeping applies.

Repeat verifier remediation until the phase verifier returns clean `PASS` with zero findings or a remediation task fails. A remediation task passing Phase 4 is not sufficient to pass the phase; it only permits another verifier attempt. To avoid an unbounded loop, allow at most `max_review_rounds` epic-gap remediation tasks per execution phase; if the limit is reached and the verifier still returns findings, stop scheduling and report `needs-human` with the latest raw verifier JSON.

The old final-only verifier behavior is now just the final execution phase's invocation. Do not run a second duplicate full-epic verifier after the final phase.

Include each phase's verifier target, verdict, remediation attempts, gap-fix task commits, integration ranges, and findings in the final report. If a task failed before a phase completed, skip verification for that incomplete phase and later phases and explain why.

## Phase 6: Final Report

Report:

- Team name and `team_hash`.
- Team tasks file path.
- Effective `max_parallel` and any tasks forced to serial scheduling because file scopes overlapped or were unsafe.
- Resolved per-task verification gate commands, including any missing coverage categories or no-op fallback reason.
- Table of tasks with `passed`, `failed`, or `skipped`, including task commit SHAs and integration ranges for passed tasks.
- Table of synthetic `epic-gap` remediation tasks, including phase, verdict that triggered them, outcome, task commit SHAs, and integration ranges.
- Failed task category: `needs-human`, `unverified-failure`, `infra-failure`, or `abandoned`.
- For failures: baseline SHA, retained state directory, raw `last_error` if present, and manual recovery options such as `git reset --hard <baseline_sha>` or `git revert <commit_range>`.
- Epic verification verdicts and findings for each completed execution phase, or why any phase verification was skipped.
- Retry note: rerunning `/cerberus:run-team` is safe after fixing the root cause because each invocation gets a fresh `team_hash`; stale state dirs remain only for debugging.
- Cleanup note: successful task hook state dirs are deleted automatically, but persistent task contexts remain under `${TMPDIR:-/tmp}/cerberus-task-completed-hook/<team_hash>/task-contexts/` until the run is cleaned up.
